# AI referee boundary · v0.1.1

**Implemented:** one strict offline intent path (`dungeon.rest`) and the original diagnostic (`diagnostic.roll`). **Not implemented:** live AI connection, general free-form parsing, encounters, and module importing. The local whitelist recognizes explicitly stated one-turn rest commands only; it is *not* a mock AI service.

Example offline player text: `The party rests for 10 minutes`.

Proposed operation, untrusted at all times:

```json
{"contract":"bx.intent.v1","baseRevision":0,"operations":[{"kind":"dungeon.rest"}]}
```

The engine checks contract, exact operation keys, one-operation atomicity, and current revision. Reject stale/unknown/additional operands **without RNG or state mutation**. An accepted `dungeon.rest` advances one 10-minute dungeon turn and consumes one turn of an active torch. At the end of every second dungeon turn the engine privately checks 1d6 for a wandering encounter (1 = encounter next turn). If triggered, it persists a *pending* event and refuses further dungeon-turn progression until a genuine encounter resolver exists; it never fabricates a monster, map, room, or result. The narrator receives **only** public outcome fields (time and light), not encounter roll/result or hidden content. A `diagnostic.roll` remains available solely for regression testing and does not advance dungeon time.

Source: **Moldvay (1981)** Basic p. B19 (10-minute turn and rest), B21 (6-turn torch), B53 (wandering check after every two turns; encounter in following turn). Cook/Marsh Expert supplements Basic but does not override these procedures. No rules were derived from BECMI or Rules Cyclopedia.

Save schema v2 records exact RNG, light, public journal and pending encounter. Legacy v1 demo saves migrate on load: preserve existing character/time/dice/journal; assign `light.kind='none'` because historical saves do **not** establish ownership of a lit torch. The initial storage key is retained. Old serialized data is validated before migration. Neither migration nor rejected proposals rolls dice.

**Future AI service boundary:** client sends player text and player-visible scoped state only; an authenticated server-side proxy owns provider credentials and validates requests; the model returns an untrusted typed proposal. The deterministic engine adjudicates, and narration receives only authorized, player-visible outcomes. Hidden adventure content should be held server-side, not inside a GitHub Pages application. No API keys or fake AI requests appear in this checkpoint.

Both repeated establishment and further dungeon turns refuse unchanged. Encounter surprise, actual identification/visibility, reactions, initiative, and combat are deliberately **not** adjudicated. The narrator receives only `{kind:'encounter.contact',stage:'awaiting-referee'}`; it does not invent sight, identification, surprise, or victory. Journal entry records the contact boundary only.

**Security limitation:** The fixture is intentionally public, and the static application and local saves are inspectable. The contact record contains this non-confidential demonstration fixture's monster, selected count, and deterministic distance; anyone inspecting local storage or code can discover them. This is not a secure referee-secret boundary or support for any proprietary module. **Do not load hidden adventure records, traps, secret room contents, private monster plans, or other confidential referee data into this client, static package, or browser save.** A future authoritative server must retain such information separately and release only approved player-visible fields after visibility adjudication. No API service, credentials, or true AI are connected in v0.1.2. The provided fixture is not an adventure or licensed adventure content.

Save schema **v3** adds exact `activeEncounter:null|contact`. Exact historical v1 and v2 saves migrate without adding unseen encounters or changing RNG/time. Pending v2 wandering events stay pending and may be established after load. An active contact remains blocked against unsupported play after reload. Acceptance tests cover the offline command, exact-data validation, deterministic replay, rejected mutations, and browser save/load.


## v0.1.3 — Original B/X surprise with information boundary

Primary rule: **Moldvay Basic (1981), p. B23, Surprise**. One d6 for each side, 1–2 is surprised. If both sides are surprised, their surprise cancels and neither side moves/fights that round. If only one side is surprised, the other can act in the initial round. When neither side is surprised, initiative normally follows. **This checkpoint records the four dispositions but implements no round, initiative, reaction, action or combat resolver.** B23 notes that some situations make surprise impossible; this public, generic goblin fixture has no situational exception. Unsupported situational modifiers or special monster exceptions remain unimplemented and must not be invented.

The strict offline command `adjudicate surprise` proposes `{contract:'bx.intent.v1',baseRevision:N,operations:[{kind:'encounter.surprise'}]}`. Only an existing unresolved active contact with an exact validated known-public fixture accepts it. Two dice are consumed in the fixed party-then-monster order, once only, atomically. Saved `activeEncounter.surprise` contains both rolls, derived booleans, and `disposition`. The independently persisted `activeEncounter.visibility` has distinct `presence`, `identity`, and `distance` fields, all `unestablished`: surprise itself does **not** establish sight, identification, sound, distance known to the party, or any treasure/room knowledge.

Narration receives **only** `{kind:'encounter.surprise',partySurprised:boolean,perception:'unestablished'}`. A party's own surprise condition may be reported; opponent roll, opponent surprise, monster identity, number, and precise distance are excluded from player-facing outcomes and status. The encounter remains mechanically blocked until later source-backed adjudication. Save schema **v4** retains all prior RNG/time/light/pending/contact data and strictly migrates exact v1/v2/v3 envelopes without new rolls or invented perceptions. Test cases cover all four dispositions, malformed and stale operations, forged saves and packet refusal, deterministic replay, and actual Chrome command/save/load.

**Security limit:** the separation is a presentation contract, **not confidentiality**. Static browser source and localStorage are inspectable and contain the public demo encounter and saved RNG. Never put actual private referee/adventure data here; secure private-world state and credentials require authenticated server authority. AI integration remains disconnected.


## v0.1.4 — evidence-gated perception with qualitative visibility

Primary 1981 B/X authority: **Moldvay Basic p. B21** establishes 30-foot ordinary torchlight; **p. B23** treats encounter circumstances and separation as referee-judged rather than automatically proving that a monster is seen. The `lineOfSight` and `recognition` evidence in `src/content/encounters/public-perception.js` is a clearly labeled, authored **PUBLIC DEMONSTRATION SCENARIO ASSUMPTION**, not an imported original rule, generated geometry, or secret adventure content.

The strict local command `assess encounter visibility` proposes only `encounter.perceive`. The deterministic engine requires the exact already-established public goblin packet, an active contact after surprise, and an independent exact validated evidence packet. It tests current recorded torchlight and numeric separation; only if illumination reaches the creature **and** authored line of sight is clear does it mark presence `visible`. Identity is `goblin` only when separate authored recognition evidence confirms it. The only distance label ever disclosed is qualitative `within-torchlight`; the exact 2d6 result, full monster count and both surprise dice remain out of narration. No sightline or recognizability is inferred from dice, torch alone, or the parser. If no evidence is sufficient, visibility remains `unestablished` (which does **not** mean monster absence).

The outcome is a minimal player-visible `{kind:'encounter.perception',visibility:{presence,identity,distance}}`. It does not expose evidence IDs or contact data. Duplicate, unsupported, stale or forged requests are rejected atomically without RNG, time, torch or character changes. A v5 save adds `evidenceId` to the active encounter and a `perception-adjudicated` phase; strict migration from v1, v2, v3 and v4 leaves perception unknown and does not reroll dice. The pending encounter remains blocked for future B/X procedures. No initiative, reactions or combat were added.

**Security:** browser source and localStorage remain readable; the sample evidence is entirely public and *not authenticated DM proof*. A future real referee must hold private adventure facts server-side and supply independently authenticated evidence. Neither this sample evidence nor the offline whitelist is a live AI parser. Do not place secret maps, monsters, traps, proprietary module notes or API keys in these client files.


## v0.1.5 — minimal encounter transition and continuity of established knowledge

Moldvay (1981) Basic **B23** distinguishes first contact, surprise, later encounter choices (fight/talk/run/wait) and the ending of an encounter; none of those later choices, initiative, monster reactions or combat are adjudicated in this checkpoint. The narrow handoff stage below is **application bookkeeping**, not a new B/X turn, reaction, combat result, or declaration that the encounter ended.

The exact offline command `handoff encounter` submits one untrusted `encounter.handoff` intent with the current revision. Only a valid active contact in `perception-adjudicated` stage accepts it. The deterministic engine increments the state revision, appends a bounded handoff record, and changes the stage to `awaiting-referee-continuation`. Its prior `surprise`, `visibility`, validated `evidenceId`, numeric distance, creature type/count, encounter dueTurn, RNG, time, light and character fields remain unchanged. Further dungeon rest, duplicate handoff and unsupported adjudication commands are still refused, **not** silently treated as a peaceful resolution.

`src/state/player-knowledge.js` projects only `{partySurprised,visibility:{presence,identity,distance}}` from already-adjudicated state. Narration and the handoff UI use this projection, retaining previously confirmed goblin/creature sighting or explicitly unestablished presence, while withholding opponent dice, identity when unknown, actual numeric range, count, fixture IDs and hidden adventure details. In the public demo, these fields are visible in static source/local saves by inspection; this is a **display/narration boundary**, never true secret protection. No new line of sight or perception test is simulated on handoff.

Save schema **v6** validates the new stage and journal action. Exact v5→v6 migration retains previously established perception without new RNG or assumed knowledge, and **refuses v5 data forged to contain the v6-only handoff stage/action**. Prior v1–v4 migration remains intact. Live AI, secure referee/server authority, surprise actions, further encounter resolution, reactions, initiative, combat, maps and modules are not connected here.


## v0.1.6 — one verified no-pursuit conclusion and resumption

**Primary rules:** Moldvay Basic (1981) **p. B23**, *Time in Encounters* and *Party Actions*: an encounter of **60 or fewer** 10-second rounds counts as **one** 10-minute dungeon turn; if the party withdraws and the monster does not follow, the encounter is over. **p. B24** governs cases involving running/evasion/pursuit, which are **not simulated** here. Basic **B21** controls the torch's six-turn lifetime and **B53** checks wandering monsters at the end of every second dungeon turn. Source authority remains original B/X, not Mentzer, Mystara, or the Rules Cyclopedia.

**Evidence contract:** `src/content/encounters/public-disposition.js` contains precisely one *public, independently authored demo scenario* with `partyDecision:'withdraw'`, `monstersFollow:false`, `combatStarted:false`, and a fixed **one-round** duration. These are **authored test circumstances**, not dice outcomes, not guaranteed by a player request, and not a general reaction or evasion rule. `src/rules/disposition-evidence.js` validates exact keys and exact canonical values. The offline parser recognizes only `resolve public demo nonpursuit`; it does **not** accept `kill goblins`, `end encounter`, or user-supplied monster behavior. The engine independently requires `awaiting-referee-continuation`, the original validated encounter packet, an exact matching disposition packet and the due turn. Failed, repeated or stale resolutions leave state and RNG untouched.

On valid acceptance, `encounter.conclude` consumes **the scheduled one dungeon turn**, reduces a lit torch by one (never negative), does **not** advance RNG because that due turn is odd, clears active contact, and stores a strictly validated `lastEncounter` archive with the pre-conclusion contact, light state and canonical evidence ID. The player-knowledge projection may use this archived contact after closure and across later exploration turns and save/reload; narration discloses only the documented escape, time/light and authorized knowledge. Subsequent `dungeon.rest` resumes; the normal B53 wandering check applies on the next even turn. No XP, treasure, victory, HP change, initiative, morale, combat, unrestricted reaction outcomes, running distance, extra rest penalty, or position has been inferred.

**Save schema v7:** exact historical v1–v6 migrations preserve prior state and add `lastEncounter:null`; no old save acquires a fabricated concluded encounter. Archive validator checks the original pre-turn snapshot and enforces known encounter facts against recorded perception evidence. Invalid, unsupported and extra historical fields refuse. The static, public browser fixture and localStorage **cannot conceal actual DM secrets**, and no live AI API or authenticated server referee exists.
